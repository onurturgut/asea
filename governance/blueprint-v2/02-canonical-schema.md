# Volume 01 Blueprint v2 Candidate — Programming Foundations

## Purpose

Define the registered Volume Blueprint container for the 12-Module,
38-Chapter, and 66-outcome Programming Foundations v2 candidate.

## Scope

The candidate preserves all existing `V01-M01`-`V01-M07`,
`V01-C01`-`V01-C28`, and `V01-LO001`-`V01-LO046` meanings. It adds five
Modules, ten Chapters, and twenty outcomes for explicit JavaScript readiness.

Academy and Track are derived portfolio views. Lesson is the learner-facing
view of one canonical Chapter. These views do not create new identity owners.

## Audience and Level

The audience is a beginner entering professional software engineering study.
The target level remains Intermediate programming readiness, now including
explicit JavaScript runtime, type, object, collection, functional, numeric,
temporal, exception, and module competencies.

## Prerequisites

`V00` remains the entry prerequisite. No existing prerequisite is removed.

## Learning Outcomes

The candidate contains 66 outcomes:

- 46 preserved outcomes with unchanged meaning;
- 20 new measurable outcomes in `V01-LO047`-`V01-LO066`;
- every outcome has one parent Chapter lesson view;
- every outcome must receive a canonical assessment mapping before Freeze.

| Entity | Authority and identity | Relationship |

| Academy | Derived catalog slug | Groups canonical Volumes |

## Practice and Assessment Map

The v2 architecture requires:

- one practical evidence artefact per Chapter;
- one Chapter assessment per Chapter;
- Module gates that aggregate outcome evidence;
- eight Mini Projects;
- one preserved Capstone `V01-CP01`;
- one Volume Final Assessment.

This Sprint designs architecture records only. Learner-facing assessment
instruments remain future production artefacts.

## Dependencies

The candidate dependency graph is stored in
[06-dependency-graph.md](./06-dependency-graph.md). It contains 38 Chapter
nodes, preserves all existing prerequisite relationships, adds explicit
JavaScript readiness edges, and must remain acyclic.

## Traceability

```text
Volume -> Module -> Chapter/Lesson -> Learning Outcome -> Assessment
Chapter location -> Claim -> Evidence -> Source
Chapter concept -> Knowledge Graph -> prerequisite Concept
Publishing Package -> Manifest -> reviewed artefact versions
```

The candidate Chapter and Learning Outcome registries provide parent and
dependency mappings. Every outcome resolves through its parent Chapter to the
planned assessment `V01-Cnn-AS01`; the complete relationship is recorded in
the Learning Outcome Registry. The 311-entry `planned_artifacts` inventory
covers eight artefact identities for each of 38 Chapters, six Mini Projects,
and one Capstone.

## Acceptance Criteria

- 12 Module records, 38 Chapter records, and 66 outcome records exist.
- All 311 planned artefact identities are enumerated without duplicates.
- Every outcome maps to one planned Chapter assessment.
- No existing ID or meaning is removed or reused.
- Dependency validation reports no cycle, orphan, or missing parent.
- Migration and rollback dry runs pass.
- ADR-017 is Accepted through an Approved review.
- Technical, Content, Repository, Governance, Migration, and Final reviews
  approve the exact candidate.
- Manifest and candidate checksums reconcile.

## Risks and Constraints

- The current v1 Freeze remains active until atomic activation.
- Academy and Track cannot become parallel curriculum authorities.
- Lesson segments cannot receive independent prerequisites or outcomes.
- New outcome statements require Content and Assessment review.
- The candidate cannot be frozen with open Critical or Major findings.

## Review and Freeze

candidate and issue a new immutable Freeze Record only after all decisions are
Approved.
